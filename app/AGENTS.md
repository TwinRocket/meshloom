# Backend (`app/`)

Backend-only rules. The working rules, commands, gate, cross-cutting conventions
(packet identities, message dedup, hashtag rule, files that must never be renamed)
and the delivery flow are in the root `AGENTS.md`. Like everything else here,
this file is a hypothesis: check it against the code. Routes: `app/routers/*.py`
and the OpenAPI page (`/docs`), not a table here.

## Seams worth knowing

- `services/radio_runtime.py` is the only way routers, the lifespan, fanout and
  `radio_sync.py` reach the global `RadioManager`. Radio access goes through
  `radio_operation()` (the radio lock).
- `radio_workarounds.py` holds an in-memory copy of the workaround settings
  (Settings → Radio → Advanced): loaded at startup, refreshed by
  `AppSettingsRepository.update()`. Write through the repository, never around it.
- `routers/server_control.py` holds the repeater/room CLI helpers shared by the
  repeater and room routers.
- `push/` is Web Push, separate from the fanout bus (`fanout/`, see `fanout/AGENTS.md`).
- `app/data/iata_airports.json` is generated by `scripts/data/refresh_iata_airports.py`
  from meshloom-community's snapshot: regenerate it, never edit it by hand.
- `services/test_channel.py` (`#meshloom-testing`, radio self-test and
  `POST /tools/mesh-test`) stores no channel and no message.
- `frontend_static.py` serves `frontend/dist`, else `frontend/prebuilt` (the release
  zip ships that one), else answers `/` with a 404 JSON explaining how to build.

## Migrations

- One file per version: `app/migrations/_NNN_description.py`, discovered by numeric
  prefix, run in order, tracked by `PRAGMA user_version`.
- Never rename or delete one (root `AGENTS.md`, "Deployments that never delete
  files"); the runner refuses two files with one number (`_refuse_duplicate_numbers`).
- Each migration runs in one transaction with the `user_version` bump;
  `conn.commit()` inside it is deferred to the runner. A migration that cannot run
  in a transaction (`VACUUM`, `journal_mode`) sets `TRANSACTIONAL = False` and must
  be idempotent.
- New indexes go in both `database.py` (fresh DBs) and a migration (existing DBs).
- Tests: `tests/test_migrations/`.
- Schema reference (tables, indexes, retention, how to add a migration):
  `docs/dev/database.md`. `tests/test_database_doc.py` fails when its table or
  index list drifts from a freshly migrated database.

## Radio lifecycle

- Transport lives in `app_settings` (`radio_transport`, `radio_serial_port` empty
  = auto-detect, `radio_tcp_*`, `radio_ble_*`). Until `radio_transport` is set, the
  radio stays paused. Legacy `MESHCORE_SERIAL_PORT` / `_TCP_HOST` / `_BLE_ADDRESS`
  are imported once into an existing database with no transport, then never read;
  a new database ignores them (`services/radio_transport.py`).
- BLE pairing (`services/ble_pairing.py`, `services/ble_agent.py`; detail in
  `docs/dev/ble-pairing.md`): on Linux with a MAC address, `_connect_ble` first
  pairs through BlueZ over D-Bus. A one-shot `Agent1` is registered on the same
  connection that calls `Device1.Pair()`, never as the default agent. After
  pairing the link is released (bleak's `BleakClient(address)` scans first and a
  connected companion does not advertise), and meshcore gets
  `create_ble(device=BLEDevice(path), pin=None)`: adapter pinned, bleak's
  agent-less `pair()` never runs. Environmental failures (no D-Bus, no
  bluetoothd, permission, no adapter) fall back to `create_ble(address, pin)`.
  The PIN format is checked only when a `Pair()` is needed (a bonded radio
  ignores it). Auth failures are sticky per (address, PIN), transient ones back
  off 5-60 s, and `reconnect()` reports each once (coded WS error without
  `details`, outside the `reconnection_failed` budget; one toast for the whole
  backoff class). A failed attempt only disconnects a link its own `Pair()`
  brought up (never another client's bonding). Explicit pair/forget routes run under
  `lifecycle_transition` then `RadioManager.ble_maintenance()` (holds
  `_reconnect_lock`, answers busy at once). Lock order: lifecycle, reconnect,
  radio operation, `ble_pairing` lock. Tests never touch the system bus: a
  conftest guard replaces `_open_bus`; `tests/fake_bluez.py` runs on a private
  dbus-daemon.
- A live key that differs from `radio_bound_public_key`, or mesh history with no
  bound key (`identity_unbound_legacy`), closes ingest and pauses setup until the
  user adopts or rejects (`POST /radio/identity/adopt|reject`). Do not call
  `pause_connection()` while the post-connect operation lock is held.
- If post-connect setup fails, `setup_complete` stays false and the monitor
  retries indefinitely. This is intentional: the radio may be rebooting. When
  setup times out (300 s) on both of its two attempts, the backend broadcasts a
  `radio_startup_stuck` error asking for a radio reboot.
- Clock sync (`sync_radio_time_outcome`, `radio_sync.py`): when the radio rejects
  the time and its clock is more than 30 s ahead (or unreadable), it is rebooted
  once per radio public key per process (recorded only once `reboot()` returned);
  setup returns `"reconnect"` before the
  device query and the monitor reconnects once the radio is back. Without this,
  the device query lands on a rebooting radio: path hash support goes undetected
  and setup hangs until its timeout.
- If the clock is still ahead after that reboot, the clock wraparound
  (`set_time(0xFFFFFFFF)`, wait for the uint32 overflow, set the time, verify with
  `get_time`) runs only from post-connect setup (`allow_wraparound=True`; the
  periodic sync and `PATCH /radio/config` never write `0xFFFFFFFF`), only with
  the `auto_clock_wraparound` setting (on by default), only for a radio more than
  `_CLOCK_WRAP_MIN_AHEAD` (1 year) ahead (a host clock days or months behind must
  not roll back a correct radio) and more than `_CLOCK_WRAP_MIN_AHEAD_OF_BUILD`
  (10 years) past the build date (a stale fake-hwclock can leave the host clock
  years behind), never for the shared `"unknown"` key (no
  SELF_INFO), at most once per connection (`id(mc)`) and once per radio key per
  process, whether it fixed the clock or not (`_clock_wrap_done`). Neither the reboot
  nor the wraparound runs while the host clock is below `_host_clock_floor()`:
  the later of `_HOST_CLOCK_FLOOR` (2026-01-01) and `_BUILD_EPOCH`, the mtime of
  `radio_sync.py` (Docker `COPY` and the deb/rpm packages keep the build
  checkout's mtime). Setup logs `Radio clock at connect` before the sync and
  `Radio clock after sync` after the device query. Tests:
  `tests/test_radio_clock_wraparound.py` (fake firmware clock).
- Whoever triggered that reboot (setup, the periodic sync, `PATCH /radio/config`),
  `RadioManager.note_expected_reboot(reason)` records it for
  `EXPECTED_REBOOT_GRACE_SECONDS` (90 s). Reasons (`ExpectedRebootReason`,
  `services/radio_lifecycle.py`): `clock_sync` (the clock fix) and `wifi_config`
  (a reboot that applies Wi-Fi settings, sent only by the Wi-Fi routes, see
  "Wi-Fi"). The user-initiated `POST /radio/reboot` records none. While it runs,
  health says `radio_state: "rebooting"` with `reboot_reason` (the frontend picks
  its copy from it), reconnect failures are not broadcast, `POST /radio/reconnect`
  (and `POST /radio/reboot` while disconnected) answers 200 `pending` with
  `code: "radio_rebooting"` and `params.reason` instead of racing the monitor,
  `POST /radio/identity/adopt` returns `radio_state: "rebooting"` instead of
  `"paused"`, and the monitor drops a transport that survived the reboot (a
  serial bridge keeps the port open) so setup runs again on a new session. The
  first completed setup clears it (`prepare_connected_radio` reports healthy only
  when the transport is up and setup completed, never after a setup that found
  no transport); past the bound the monitor broadcasts only
  `radio_reboot_timeout` (`params.reason`) on that pass, then reconnect errors
  surface again. Monitor logs name the reason; the debug snapshot shows it
  (`runtime.expected_reboot_reason`).
- A broadcast `error` with a `code` is translated by the frontend from
  `errors.<code>`; its details from `errors.<code>Detail` when that key exists,
  else the backend's `details` are shown as sent.
- The message poll task always runs: an hourly audit, or every 10 s with
  `enable_message_poll_fallback`. It also detects channel-slot cache drift.
- `sync_recent_contacts_to_radio()` sets `_last_contact_sync` before the sync
  finishes, so a failed sync stays throttled (no retry storm).
- The `meshcore` reader can raise `IndexError` on a truncated advert `LOG_DATA`
  frame: a library parsing gap. That packet's task fails; later packets still process.

## Wi-Fi (companion CLI)

- `services/radio_wifi.py` owns the Wi-Fi feature and its CLI sessions (routers
  in `routers/radio_wifi.py` only validate, check 423 and map coded errors). It
  uses lot A's helpers (`store_wifi_credentials()` and friends); never send
  `wifi.*` commands any other way.
- **Never a password in the DB or a log.** The stored password is read only to
  learn whether credentials are stored: by the full check (after each connect,
  its retries, or `GET /radio/wifi?refresh=true` when no check completed) and
  inside `store_wifi_credentials()` (one read before, one read-back). A refresh
  after a completed check never reads it. No route returns it; there is no
  `set wifi.clear` route.
- **Prompt state** (`app_settings.wifi_prompt_state`, migration 095, not in
  `AppSettings`): JSON keyed by the lowercase radio public key with independent
  fields: `dismissed_at` ("don't ask again", never erased), `open_network_ssid`
  (an open network reads like "nothing stored"; the full backup exports it
  from this record), and the **store-in-progress
  marker** `store_started_at`/`store_target_ssid`, written before the first `set`
  and cleared once the store is verified or rolled back, or when it failed
  before its first `set` (any non-`CliError`, such as a dropped link, comes from
  there); kept on `wifi_store_partial` or a cancellation, it makes the state report `store_incomplete` (and
  `credentials_stored` false) after a reconnect until a verified store. Every
  repository helper is one `json_set`/`json_remove` UPDATE.
- **After each connect** setup calls `start_post_connect_check()`: it clears the
  cache and spawns (through `spawn()`) one task, bound to that connection when it
  is spawned, that runs the full check, retries a failed one at 30 s and 120 s
  (`check: "failed"`, `next_retry_at`; a retry is skipped once a manual retry
  completed a check), then re-checks status/IP only (non-blocking sessions) at
  10, 30 and 60 s while Wi-Fi is enabled but not joined. It stops without writing
  once its connection is gone (generation + `cli_link` identity), and never
  stores credentials.
- **Cache writes are ordered**: a state is written and broadcast inside the
  session that computed it, only for its connection and only if no newer write
  landed (version); re-checks merge `connected`/`ip` only. A dismissal (no radio
  lock) patches `prompt_needed` without bumping the version, and every later
  write of this connection applies it, so a store in flight is not lost. The
  cache is cleared
  in `RadioManager._reset_connected_runtime_state()`.
- **Reboots**: whether a change needs one is decided after the store
  (`wifi_reboot_required()`, with the flasher shortcut: nothing stored, same SSID,
  joined now, a password). A reboot is sent only when the request says
  `reboot: true` or through `POST /radio/wifi/reboot` (the prompt's follow-up,
  the panel's "Reboot now" and the full backup restore's reboot after its Wi-Fi
  step), both followed by `note_expected_reboot("wifi_config")`. Never use the
  generic `POST /radio/reboot` for a Wi-Fi change: it records no planned reboot, so a serial
  bridge survives, setup and the Wi-Fi check do not run again and reconnect
  errors are broadcast. Never reboot after `wifi_store_unverified` or
  `wifi_store_partial`.
- **Full backup restore.** Its Wi-Fi step calls `store_restored_credentials()`
  and `refresh_after_restore()` inside the restore's own CLI session, so the
  marker, the open-network record and the cached state follow the same rules
  as a store from the panel (see "Backups").
- **No prompt during a restore.** While a full backup restore job runs
  (`backup_restore.restore_job_running()`), `_write_cache()` holds
  `prompt_needed` False and keeps the unheld value (`prompt_wanted`); the job
  calls `reevaluate_prompt()` when it starts and when it ends (`_set_running()`),
  which patches the cached state without bumping the version and broadcasts
  only a change, so the prompt closes in every tab and comes back afterwards
  if it is still needed.
- `radio_wifi` WS event (`RadioWifiState`), broadcast with `realtime=False`
  (WS clients only, never the proxy, fanout or Web Push).
- `POST /radio/transport/revert` restores `previous_transport` on the server (BLE
  PIN included; the browser never holds it) and is what the Wi-Fi panel's "Go
  back" calls after a switch to TCP.
- Tests: `tests/test_radio_wifi_service.py`, `tests/test_radio_wifi_router.py`
  (including a WAL file scan for the password), `tests/test_radio_wifi_no_egress.py`.

## Sending

- Routers validate, then delegate to `services/message_send.py`.
- **Byte limit, one helper.** `app/message_limits.py` holds the limits (DM 156 bytes;
  channel `max(1, 156 - len(sender name) - 2)`, 10-byte name fallback when the radio
  name is unknown; UTF-8 bytes). The three services in `message_send.py`
  (`send_direct_message_to_contact`, `send_channel_message_to_channel`,
  `resend_channel_message_record`) call it, so REST, bots, the radio proxy and both
  resends are covered; a new send path must call it too. Refusal: coded 400
  `message_too_long` with `params.limit` and `params.bytes` (`errors.message_too_long`
  in the UI). The constants are "empirically determined" from the firmware's packet
  budget; `tests/test_message_limits.py` reads the composer's TSX constants and fails
  when they drift or are not found.
- Channel slots are reused through a session LRU cache, except on TCP or with
  `force_channel_slot_reconfigure`, where every send calls `set_channel(...)`.
- Path hash modes `0`/`1`/`2` mean 1-, 2- and 3-byte hop IDs. `path_len` in the
  API is always a hop count.
- DM route precedence: override, then learned direct route, then flood.
  Advertisement paths (`contact_advert_paths`) are never used as send routes.
- DM retries mirror `meshcore_py` `send_msg_with_retry`: retry up to 2 more times
  only when `MSG_SENT` returned an expected ACK code; the last retry is flood
  (`reset_path`). The first ACK is terminal: sibling ACK codes are cleared.
  ACKs never update routes.
- Channel resend: byte-perfect within 30 s; `?new_timestamp=true` has no time
  limit and creates a new row. The web UI sends `?client_age_seconds=` (its
  browser-clock age, authoritative for the window): the 30 s check then uses it,
  and the server clock only refuses messages older than 300 s
  (`RESEND_CLIENT_AGE_MAX_SERVER_ELAPSED_SECONDS`). Without it (bots, older
  clients, or the UI when it has not measured the clock skew) the 30 s window is
  measured on the server clock, as before. Expiry is a coded 400
  (`resend_window_expired` / `resend_window_expired_server`, `params.seconds`).
  The echo watchdog (auto-resend) stays on the server clock.
- Repeater/room login (`prepare_authenticated_contact_connection`): one try on the
  effective route, then exactly one flood retry, only on timeout and only when the
  route was not already flood. Deliberate: the server relearns the return path on
  a flood login. Do not reduce it to single-shot, and do not add a client retry.

## Companion CLI and secrets in logs

- **One seam.** Companion CLI commands (firmware v1.18, command 66) go through
  `services/companion_cli.py`: `companion_cli_session(name)` takes the radio lock
  with polling paused and auto-fetch suspended, refuses with `setup_incomplete`
  before setup completes (checked again once the lock is held, before auto-fetch
  is stopped), and yields a `CompanionCli`. Code that already holds
  the lock (setup, a `radio_operation()` block) builds `CompanionCli(mc,
  manager=...)` inside `mark_radio_lock_held()`. Never call
  `mc.commands.run_cli_command` directly.
- **Owner task.** `run()` refuses unless the calling task itself holds the lock,
  so a task spawned inside a session is refused. Never wrap a CLI call in
  `asyncio.wait_for`/`shield`/`gather` (on 3.11 they run it in a new task); use
  `run(timeout=...)` or `async with asyncio.timeout(...)`.
- **Gate.** `capabilities()` and `run()` send nothing when `firmware_ver_code` is
  unknown or below 14, or through a Meshloom radio proxy (it reports fw ver 10
  and a `MeshloomProxy/` model: `proxy_link`); `run()` raises
  `CliUnsupportedError` with that reason (`cli_gate_reason()`). Otherwise
  `capabilities()` probes `get wifi.status`: `untagged`, `unsupported_cmd`
  (ERROR(1) with no tagged reply after a 1 s grace; forks and pre-release builds)
  and `link_unreliable` stick until reconnect, and `run()` refuses them too;
  `probe_failed` backs off 30 s, five failed probes per connection at most. Each
  probe outcome is logged at INFO. The debug snapshot (`companion_cli`) shows the
  gate reason, else the last probe result, else null: nothing in the backend
  probes on its own, a feature does when it needs the CLI.
- **Tags are the reply guard.** CLI replies carry no request id. Each command
  starts with a 2-byte `XY|` tag that the firmware echoes; only a reply with our
  tag is accepted. Tags come from `RadioManager.cli_link` (`CliLinkState`: random
  start, replaced with the connection; each setup drops only the probe cache and
  keeps the tags and the quarantine); a call that ends without its reply
  quarantines its tag, and more than 64 quarantined tags declare the link
  unreliable.
- **Secrets.** The helper classifies commands itself: `set`/`get` of a name
  containing `pwd`, `pass`, `key`, `secret` or `pin` (and `SENSITIVE_COMMANDS`)
  is secret or a sensitive read, and so is any call given explicit `secrets`
  (`run(..., secrets=...)`, `set(..., secret=True)`). No `set` argument, no
  sensitive reply and no command text in a log line or an exception: for a
  secret command they show only a verb and a name that look like a setting name
  (never the argument of a one-word secret verb such as `password`). `reboot`,
  `poweroff`, `shutdown`, `erase` and `start` are refused: reboot with
  `mc.commands.reboot()` plus `note_expected_reboot()`. Never set `CONTACT_FLAG_REMOTE_CLI` (0x10), and never
  use the remote CLI over the mesh.
- **Never log a Wi-Fi password or a private key, at any level.**
  `app/log_redaction.py` enforces it for what meshcore logs: a filter at index 0
  of the `meshcore` logger (structural rules on the frame codes 0x42/0x18 out,
  0x1D/0x0E in, plus `secret_scope()` literals), a redacting formatter on the
  app's handlers (tracebacks included), `bleak`/`dbus_fast` clamped to INFO
  (their DEBUG output dumps every BLE frame: `bluezdbus/client.py` write on
  Linux and Raspberry Pi, `corebluetooth/client.py`, `bluezdbus/manager.py`), and
  an app-wide 422 handler that drops each error's `input` and `ctx`.
  `tests/test_meshcore_log_sites.py` pins the meshcore log calls: on a meshcore
  or bleak bump, review the rules, then refresh its fixture.
- **Mandatory for every model with a secret field:** `SecretStr` and
  `model_config = ConfigDict(hide_input_in_errors=True)`. A `ValidationError`
  raised in service code is a 500 logged with `str(e)`, which carries the input
  otherwise. Copy the 500-path test of `tests/test_log_redaction.py` for it.
- Tests: `tests/test_companion_cli.py`, `tests/test_log_redaction.py`; the
  loopback fixture `tests/fixtures/meshcore_loopback.py` runs the real meshcore
  stack against a fake v1.18 firmware.

## Read state

`GET /read-state/unreads` never windows the whole `messages` table: it enumerates
conversations with an index skip-scan. `tests/test_unreads_equivalence.py` keeps
the old `ROW_NUMBER()` query as an oracle: both outputs must stay identical.
`first_unread_ids` is the first unread row by `(received_at, id)`; `MIN(id)` would
be wrong, because historical decryption inserts old messages with new ids.

## Backups

- **Three kinds.** `GET /settings/backup/database` (a SQLite snapshot, never
  restored from the UI, no private key); `meshloom-backup-v1` (`export_json` /
  `restore_json`, Meshloom data only; `GET /settings/backup/json` stays v1 for
  scripts); and the full backup `meshloom-backup-v2` (`POST
  /settings/backup/export`): the v1 fields unchanged plus `identity`, `radio`
  (`RadioNodeSettings`), `wifi` and `meshloom_extra`. Code:
  `services/backup.py` (formats, coverage, export, Meshloom restore),
  `services/backup_radio.py` (radio reads and writes),
  `services/backup_restore.py` (identity decision, inspect, restore job),
  `services/backup_crypto.py` (envelope), `services/backup_sections.py` (sections, hooks).
- **Sections and restore hooks** (`services/backup_sections.py`, contract in
  `docs/dev/backup.md`). Other features add a named entry to the v2 file's
  optional `sections` with `register_backup_section(name, export_fn,
  restore_fn, *, description=..., sensitive=..., version=..., requires=...)`,
  never a new top-level field or a second v2 format; the job restores them in
  its `meshloom` step after `meshloom_extra`, each in its own `db.tx()`
  (`restore_fn(section, conn)` writes through `conn` only; a failure rolls that
  section back and the others go on), skips a section newer than its owner
  (`section_too_new`) and ignores unknown ones with a log line. Inspect lists
  them (`sections[]`: description, sensitive, known, too_new); a sensitive
  section exported without a passphrase adds
  `section_sensitive_unencrypted:<name>`. `register_on_restore(name, hook)`
  runs once per restore: a flat v1 restore, a job that wrote something (the
  job passes `run_hooks=False` to `restore_json` and runs them at its end), or
  a SQLite snapshot put back in place (the download carries a
  `meshloom_backup_snapshot` table; the lifespan runs the hooks after
  `db.connect()` and drops it). The JSON export refuses (500
  `backup_identity_seed_leak`, coded on both routes) any document holding an
  `app_settings.*_seed` value, and the SQLite copy has every `*_seed` column,
  the BLE PIN and the previous-transport snapshot set to NULL (under
  `secure_delete`): instance identity seeds are never exported. Inspect and
  restore bodies over 64 MiB are a 413 `backup_too_large`.
- **Coverage.** `BACKUP_COVERAGE` gives every `app_settings` column and every
  table a decision with a reason; `tests/test_backup_coverage.py` fails on a new
  column or table until it is listed (one direction: extra entries are fine).
  The v1 settings are one list, `V1_SETTING_COLUMNS`, used by both the coverage
  and the restore; the test checks each is an `AppSettings` field and an
  `AppSettingsRepository.update` argument.
  Excluded on purpose: Community opt-in and state (consent), the radio transport
  (machine-specific), the identity binding, history and caches.
- **Secrets in the file.** `BackupIdentity.private_key`, `BackupWifi.password`
  and `BackupVapid.private_key` are `SecretStr` revealed only under the
  serialization context `{"backup_export": True}` (`export_document()`); every
  other dump, repr and the restore job show the mask, and a restore refuses the
  mask. The export route returns a `JSONResponse` from that dump, never a
  `response_model`. The key comes from the keystore (filled once per
  connection by setup); when it is empty and the firmware did not answer
  DISABLED, the export asks the radio once more inside its CLI session, and it
  falls back to meshcore's cached `self_info` key when its own appstart read
  fails. The Wi-Fi password is read live (`wifi_stored_password`) and
  never written to the database. With a password stored and no SSID, `get
  wifi.ssid` answers the compile-time fallback SSID, and the firmware gives no
  way to tell it from a stored one: the backup pairs that SSID with the
  password, and a restore stores both (stated on the public backup page too). Errors list field paths only
  (`backup_invalid`).
- **Envelope** (`meshloom-backup-v2-encrypted`): scrypt (writes N=2^16, r=8,
  p=1) over the NFC passphrase, AES-256-GCM, AAD = canonical JSON of a fixed
  header tuple. Decrypt accepts one step more than it writes (N up to 2^17, the
  OWASP figure), so a later version can raise the written N without older
  readers refusing its files; N above 2^17 needs a new format string. Decrypt
  refuses N outside 2^14..2^17, r≠8, p≠1, bad salt/nonce
  sizes or more than 16 MiB before any KDF call; encrypt refuses a plaintext
  over the same `MAX_CIPHERTEXT_BYTES` (400 `backup_too_large_to_encrypt` from
  the export), so it never writes a file the restore cannot open. KDF calls run
  one at a time in a worker thread.
- **Identity.** `decide_identity_restore(gate, bound, live, backup,
  has_history)` is the one table (TR-1 plan C.4, `tests/test_backup_identity_decision.py`):
  inspect, the synchronous 409s and the job all use it. The job decides once
  outside the `lifecycle_transition` and enters it only for an import, a wipe
  or a bind (entering it closes ingest, and only post-connect setup opens it
  again), then decides again inside, right before acting; leaving it without
  setup (a refusal, a refused import) reopens ingest for the same session, or
  runs setup when the key changed. A known live key
  other than the backup's needs `replace_live_identity` and
  `expected_live_public_key == live`; history under another key needs
  `wipe_history`; history with no bound owner (row 12, or an unbound database
  with history) is kept unless the request sends `wipe_history`, which inspect
  offers as `identity_allows_wipe` (an unchecked box in the UI); a radio that is not connected never gets the backup key bound
  (rows 3-4: the next connect opens `identity_unbound_legacy`). The job imports
  first (re-read of the live key after the reconnect on every path, refused
  with `live_identity_changed` when it moved; raw `0x18` frame waiting for
  OK/ERROR/DISABLED, then a re-read), then wipes, then binds and runs setup; any identity failure stops the job and
  pauses the link when the gate was open.
- **Restore order** (owner decision): identity, Meshloom data (only the settings
  present in the file; `meshloom_extra` through the route code paths: fanout
  validation shared with the create route, `system:*` ids refused, bots
  restored disabled and skipped while bots are disabled, VAPID keys and
  subscriptions only on a host with no subscriptions of its own, proxy through
  `services/radio_proxy_settings.py`), then in one companion CLI session: radio
  settings group by group (no clock sync per group, one at the end; a reboot
  then skips the rest; `tx_power` is a signed byte meshcore reads unsigned, so it
  is read as int8, and a negative power is written back with a raw `0x0C` frame
  since `set_tx_power` refuses it), channels into slots `0..n-1` with raw `0x20` frames (the secret is
  never re-derived from a `#name`; the slots above are emptied and dropped from
  the slot cache), contacts (reconcile stopped and always restarted, an
  unreadable table fails the step `radio_contacts_unreadable`,
  non-selected radio contacts removed first, favourites first, 0x10 always
  stripped, favourite bit from Meshloom's `favorite`, cleared under auto-evict),
  Wi-Fi last, through `services/radio_wifi.py` inside the restore's session:
  the credentials with `store_restored_credentials()` (the Wi-Fi panel's
  store-in-progress marker around the store, cleared after the verified
  read-back and kept on `wifi_store_partial`; a reboot required only by
  `wifi_reboot_required()`), then the on/off flag as its own item, then
  `refresh_after_restore()` writes and broadcasts the panel's state (no
  second password read after a verified store; a read failure writes a
  `failed` state). `BackupWifi` may carry only `enabled`
  (no credentials stored), or an open network: `open_network` with an empty
  password, exported only when the panel's `open_network_ssid` record for the
  live key matches the SSID and no store marker is left (the radio reads it as
  "nothing stored"); an SSID with an empty password is always an open network,
  and its restore stores `set wifi.pwd ` and records it again; inspect sets `wifi_off_on_tcp` when the file turns
  Wi-Fi off on a TCP link, and the UI defaults the step off. Raw frames also for the default flood scope (keeps a
  non-derived key) and auto-add (keeps `max_hops`).
- **Job.** One at a time (409 `backup_restore_running`, answered by the route
  before an encrypted file's KDF), `spawn()`ed, in memory
  (last 5); `GET /settings/backup/restore/jobs/{id}` and `/latest`. The decrypted
  document lives in the run object only and is dropped when the job ends. The
  reboot the restore offers (`result.reboot_required`, set only by the Wi-Fi
  step) is `POST /radio/wifi/reboot` whenever the Wi-Fi step wrote an item
  (`restoreWroteWifi()` in `BackupRestoreFlow.tsx`): a planned `wifi_config`
  reboot, so reconnect errors stay quiet, setup and the Wi-Fi check run again
  and the switch-to-TCP toast is armed. Otherwise the plain `POST /radio/reboot`.
  Outcomes that are not a step status go in `result.warnings` (`code` or
  `code:param`) and in a step's `items`; the UI translates every one (keep
  `frontend/src/test/backupRestoreFlow.test.tsx`'s code list in sync). Nothing a
  restore writes is broadcast: the Settings flow reloads the client
  (`onBackupRestored`), the identity window runs the identity-adopt reload.
  Both decide from the steps (`restoreChanges`: identity restored/bound, or
  Meshloom data done), never from `job.state`, since a job can fail after the
  identity step. The identity window cannot be closed while a job runs. Only
  Settings > Database mounts the flow with `resumeLatest`: a job that ended
  while no view was open gets its reload once, when that section next opens
  (handled job ids in sessionStorage); until then the client keeps its old
  contacts and conversations. That section shows the latest job while it runs,
  or finished until a view handled it; a handled job is not shown again.
- **Inspect** also lists the non-bot integrations with their `enabled` flag,
  the file's proxy setting, `bots_will_be_skipped` and `push_targets` (label and
  endpoint host of each push subscription the restore would write, per
  `push_restore_applies`): integrations, the proxy and push subscriptions come
  back as in the file and start at once, so the summary names them.
- **Restore body.** `POST /settings/backup/restore` reads a raw dict: no
  `backup` key is the v1 flat request (synchronous); a `backup` key starts the
  job (202). A file without `format` is v1 everywhere.

## Region-scope stats (`GET /statistics` → `region_scope_24h`)

Traffic (`path_utils.bucket_region_scope`, flood GroupText including undecryptable
packets) and Senders (distinct decrypted senders) have different denominators and
are not meant to agree. `false_positive_floor` comes from undefined payload types
(`0x0C`–`0x0E`) claiming `TRANSPORT_FLOOD`. Show `scoped_messages` next to the
floor, never the percentage alone, and do not remove the floor.

## WebSocket (server side)

- **Origin before accept.** `routers/ws.py` calls `reject_foreign_origin()`
  (`app/websocket.py`) before `ws_manager.connect()`: an `Origin` whose host
  and port (missing port = the scheme's default) differ from both `Host` and
  the first `X-Forwarded-Host` is closed with 1008, which uvicorn sends as an
  HTTP 403 (no frame). No `Origin` is accepted (scripts, meshenger);
  `Origin: null` is refused. Trusting `X-Forwarded-Host` is safe against
  CSWSH because a browser page cannot set it; DNS rebinding is the `Host`
  guard's job, not this one. Keep a new WebSocket route behind the same call.
  Not shared with the HTTP CORS rule yet (MSHL-5).
- On connect the server sends `health` only; contacts and channels load over REST.
- Each client has a bounded queue drained by one writer task, so
  `broadcast_event()` never awaits socket I/O. A slow client first loses
  best-effort frames (drop-newest once its backlog reaches the type's limit:
  `community_packet` at 256, `raw_packet` at 1024), then is evicted (close 1013)
  when the 2048-frame queue is full. Every other frame type carries state and is
  never dropped. Drops are counted (`ws_manager.dropped_frames`) and logged at
  most once a minute per client. Never call `websocket.send_text` on a managed
  socket: use `ws_manager.send_raw`.
- When `realtime=True`, `broadcast_event()` also notifies the radio proxy and
  dispatches to fanout and Web Push; `realtime=False` (historical decryption)
  skips all three.
- When a change touches an API or WS payload, update `frontend/src/types.ts`
  and the frontend tests in the same PR.

## Community client

Mechanics and constants: `docs/dev/community-client.md`. Contracts:
`meshloom-community/docs/contracts/` (`identity.md`).

- **Fixed addresses.** `DEFAULT_BROKER_HOST` / `DEFAULT_API_BASE` are read at call
  time by `get_community_effective()` (tests monkeypatch them; never import them by
  value). No env var is read; a new DB starts off.
- **One guard for every egress.** HTTP (`stats_request`), the Live socket, the
  release mirror, hashtags, the directory and observer reach all go through
  `community_egress_state()`, which answers None while off **and while waiting for
  a position**. `community_enrolled_state()` (on, waiting or not) is reserved to
  `FanoutManager.sync_system_modules()`, the Stats publisher and the
  `PUT /v1/me/iata` binds.
- **Four bounded exceptions**, each scoped by a context variable read by
  `stats_request`: the leftover status clear (`community_status_clear.py`), the
  join bind (`_bind_state`), the opt-out call and its manual retry
  (`_opt_out_state`), and the on-click IATA suggestion (`_iata_suggest_state`,
  never during an opt-out). Do not add a fifth without an owner decision.
- **IATA changes.** `PATCH /community` never changes the IATA (another code →
  409 `iata_requires_bind`) and never turns Community on (off → on: 409
  `join_requires_bind`, nothing written, nothing sent). An IATA change, or a
  join (`enable: true`), is `PUT /community/me/iata`: retire the old status →
  bind → save and reconnect, under `_update_lock`. A refused bind changes nothing.
- **Opt-out.** `community_teardown()` runs in a `finally` through
  `_run_to_completion()`: a failure or a cancelled caller still gets the whole
  teardown (fail closed). An unconfirmed opt-out is kept as pending and resent only
  by hand (`POST /community/opt-out/retry`), never automatically.
- **Position.** The browser never supplies a position (`CommunityIataBindRequest`
  has no `lat`/`lon`). The bind carries it exact only when the adverts broadcast
  it, else rounded to 2 decimals (`observer_position.py`). The local advert fill
  (`observer_reach.py`) makes an ear `exact` only from a full 64-hex key match;
  a placement by name stays `rounded` (no distance), and a prefix is never used.
- **Hashtag names** are published only for a `#` channel whose key is derived
  from its name (`is_public_hashtag_channel`); a `#` name on a channel with its
  own secret is private and never leaves.
- **Parsing.** An unknown `position_precision` parses as `null`, so a successful
  bind never turns into a 500.
- **Live relay** (`community_live.py`): one process-wide upstream socket; frames go
  to every WS client and the browser filters them; the guard runs before every
  attempt; a 4002 close and a 403 `banned` are terminal until `POST /community/live/restart`; 4003–4005
  are never shown to the user; the radio's IATA is always in the upstream filter.
- **Banned key** (`community_ban.py`): a Community 403 `code: banned` stops the
  six write routes locally (403 `community_banned`), Live (state `banned`) and the
  Stats publisher's reconnects for 12 h, until a restart or a user action
  (`PATCH /community`, a join or IATA bind, `POST /community/live/restart`). A broker
  auth refusal of the publisher sends one side-effect-free probe (`probe_community_ban`,
  at most hourly) so a publish-only instance learns the ban too. Never retry a ban in
  a loop.
- `tests/test_community_off_no_egress.py` sweeps the routes and checks that
  nothing leaves while off or waiting: keep any new call path covered there.

## Updates

**The root side never reads anything the app writes.** The app runs as the
unprivileged user `meshloom`; only these paths cross the boundary (the header
comments of `pkg/nfpm/apply-update`, `scripts/setup/helpers/compose-update`,
`install.sh` and `services/update_apply.py` point here):

- **Trigger, app to root.** The app writes `/var/lib/meshloom/request-update`;
  `meshloom-update.path` (`PathChanged=`) starts `meshloom-update.service`, and
  polkit lets `meshloom` start only that unit as a fallback. The helper never
  reads, deletes or chowns the request file.
- **Target.** `pkg/nfpm/apply-update` upgrades only the `meshloom` package from the
  signed repository (`signed-by=` / `gpgcheck=1`, apt pin), fails closed if that
  source is not signature-checked, and has a 120 s cooldown.
- **Status, root to app.** The helper writes `/var/lib/meshloom-update/status.json`
  (root-owned `StateDirectory`, 0644); the app only reads it. The app keeps its own
  memory in `update-attempt.json`, in its data directory.
- **Compose installs** use `scripts/setup/helpers/compose-update` on the host, same
  trigger model. The target is the latest GitHub release, pinned by digest from the
  signed `OCI-DIGESTS` (`gpgv` against the embedded keyring); downgrades are
  refused; its status is mounted read-only. The pre-4.18 helper read
  `update-job.json` from app data: the app deletes that file before triggering such
  a helper (`start_compose_helper`).
- **No apply support** for the Home Assistant add-on, plain containers and source
  installs: they only report the available version. `addon` is declared by
  `MESHLOOM_INSTALL_KIND`, never inferred; `MESHLOOM_UPDATE_HELPER=none` forces
  apply off (`services/install_kind.py`).
- The browser never calls GitHub; `services/oss_updates.py` does, and uses the
  Community mirror only while Community is on.
- Tests: `tests/test_update_apply.py`, `tests/test_install_kind.py`,
  `tests/test_oss_updates.py`, `tests/test_update_helpers_exec.py` (runs the real
  helpers against hostile inputs).

## Telemetry alerts and notifications

- Secrets (SMTP password, webhook secret in `notification_destinations`) are
  returned as `********`; a PATCH that sends `********` back keeps the stored value.
- The email transport builds an Apprise `mailto` URL on the fly from the SMTP
  settings; the URL is never stored. The HTML email references no remote content
  (inline `cid:` logo, no remote image, no link).
- Tracking a node writes a per-node override with `alerting: false`, so its alerts
  stay off until the user turns them on. Untracked nodes never alert; a poll skipped
  because the radio was busy is not a miss.
- The polling interval is clamped by the daily ceiling (`telemetry_interval.py`);
  the stored choice is not changed.

## Web Push (`app/push/`)

VAPID subject: `app_settings.vapid_subject`, falling back to `DEFAULT_VAPID_SUBJECT`;
Apple rejects `.local`. `policy.conversation_is_enabled` (mirrored by
`frontend/src/utils/pushPolicy.ts`) decides per conversation. A push service
answering 403, 404 or 410 deletes the subscription.

The test routes (`POST /push/subscriptions/{id}/test`,
`POST /settings/notification-destinations/test`) send to a destination the
client chose: they answer coded details only (`push_delivery_failed`,
`push_stale`, `push_timeout`, `notification_test_failed`,
`notification_destination_invalid`), never the exception text, which would be
a LAN-scanning oracle. The log gets the exception type only (plus the
webhook's host and HTTP status), never its text: an `httpx.HTTPStatusError`
carries the full webhook URL and its token, a `WebPushException` the push
service's body (`tests/test_test_route_error_oracles.py`).

## Route behaviours that are easy to break

- `GET /radio/private-key` is ungated (404 when the keystore is empty);
  `MESHCORE_ENABLE_LOCAL_PRIVATE_KEY_EXPORT` is retired (`RETIRED_ENV`).
- `POST /radio/factory-reset` sends nothing unless `confirm_name` equals the radio name.
- `PATCH /radio/config` reads the client repeat flag with a fresh device query
  before it sends new radio parameters (the firmware reads a missing repeat byte
  as "off"), and answers 422 when the radio rejects the name, coordinates, TX
  power or radio parameters (`apply_radio_config_update` checks every reply).
  Parameters the radio refuses (its own ERROR frame, not meshcore's timeout
  ERROR `{"reason": ...}`) with repeat on are sent once more with repeat off (the
  firmware allows repeat only on some bands); the answer's `warnings` then holds
  `client_repeat_not_allowed` and the UI shows it. The restore uses the same path.
- `PATCH /radio/proxy` answers 409 to a port change under `MESHCORE_MANAGED_PORTS`.
- `DELETE /channels/{key}`: the canonical Public channel cannot be deleted (400).
- `DELETE /messages/{id}` is local only.
- Bots: create/patch answer 403 while bots are disabled (`MESHCORE_DISABLE_BOTS`).

## Known non-issues

- `meshcore` 2.3.15 `confirm_factory_reset()` sends `0x33` without the `reset`
  suffix the firmware requires; Meshloom sends the raw frame `b"\x33reset"`.
- `sender_timestamp` is 4-byte Unix seconds on the wire. Dedup is per second, and
  switching to milliseconds would break echo dedup.
- Our own DM heard back over RF attaches `packet_hash` to the row stored by the
  send endpoint; it does not create a second row.
- Contact lat/lon `0.0` is MeshCore's "no GPS" value and overwrites older
  coordinates on purpose.
- `meshcore` 2.3.15 `import_private_key()` waits only for OK/ERROR: a firmware
  built without key import answers DISABLED, which shows up as a timeout.
- Repeater/room login passwords, channel secrets and the BLE PIN still reach the
  DEBUG logs (meshcore frame dumps), and app code logs channel names and keys at
  INFO (`routers/channels.py` channel creation, `services/message_send.py`); only
  the Wi-Fi password and the private key are redacted for now (follow-up). The
  user docs say so; keep them in step.
