# Backend (`app/`)

Backend-only facts. The repo map, commands, quality gate, cross-cutting conventions (packet
identities, message dedup, path hash modes, channel keys), environment variables, the release
chain, the updater security principle and the working rules are in the root `AGENTS.md`.
Like everything else here, this file is a hypothesis: check it against the code.

In short: the backend talks to one radio, stores what it hears in SQLite and exposes it to the web interface over REST and a WebSocket.

Stack: FastAPI, aiosqlite, Pydantic v2 (+ pydantic-settings), `meshcore` (PyPI), PyCryptodome, httpx, Apprise (email alerts and the `apprise` fanout type).

## Migrations

Migrations change the shape of the database when the program is upgraded.

- One file per version: `app/migrations/_NNN_description.py`. The runner discovers files by numeric prefix and runs pending ones in order.
- Never rename or delete a migration. Some deployments (Portainer GitOps) keep files deleted upstream, so the old name would stay on disk and run too. The runner refuses to start when two files share a number (`_refuse_duplicate_numbers`).
- Each migration runs in one transaction with the `user_version` bump. `conn.commit()` inside a migration is deferred to the runner. A migration that cannot run in a transaction (`VACUUM`, `journal_mode`) sets `TRANSACTIONAL = False` and must be idempotent.
- New indexes go in both `database.py` (fresh DBs) and a migration (existing DBs). Example: `idx_messages_chan_unattributed_sender` (migration 086).
- Tests: `tests/test_migrations/`.

## Radio lifecycle

How the program connects to the radio, keeps the link alive and notices when it is a different radio.

- Transport lives in `app_settings` (`radio_transport`, `radio_serial_port` empty = auto-detect, `radio_tcp_*`, `radio_ble_*`). Until `radio_transport` is set, the radio stays paused.
- A live key that differs from `radio_bound_public_key`, or mesh history with no bound key (`identity_unbound_legacy`), closes ingest and pauses setup until the user adopts or rejects (`POST /radio/identity/adopt|reject`). Do not call `pause_connection()` while the post-connect operation lock is held.
- The connection monitor checks every 5 s. If post-connect setup fails, `setup_complete` stays false and the monitor retries indefinitely. This is intentional: the radio may be rebooting.
- Clock sync (`sync_radio_time_outcome`, `app/radio_sync.py`): when the radio rejects the time and its clock is ahead, it is rebooted once per process. Setup then returns `"reconnect"` before the device query, and `prepare_connected_radio()` drops the transport so the monitor reconnects once the radio is back. Without this, the device query lands on a rebooting radio: path hash support goes undetected (the 2-byte default is not applied) and setup hangs until its timeout.
- Dev-only switches (never in user docs; table in the root `AGENTS.md`, "Dev-only variables"): `MESHCORE_SKIP_POST_CONNECT_SYNC` skips the post-connect sync here, `__CLOWNTOWN_DO_CLOCK_WRAPAROUND` enables the wraparound attempt in the clock sync above.
- If setup exceeds 300 s, the backend logs the failure and broadcasts an `error` toast asking the operator to reboot the radio and restart the server.
- The message poll task always runs: an hourly audit by default, or every 10 s with `app_settings.enable_message_poll_fallback` (Settings → Radio → Advanced; a change restarts the loop through `restart_message_polling_if_running()`). It also detects channel-slot cache drift and resets the send-slot cache when it finds any.
- Periodic adverts: `app_settings.advert_interval` in seconds, `0` = off. Any non-zero value is floored at 3600 s (`MIN_ADVERT_INTERVAL`).
- `sync_recent_contacts_to_radio()` sets `_last_contact_sync` before the sync finishes, so a failed sync stays throttled (no retry storm).
- Contact capacity: `max_radio_contacts`. Favorites load first, non-favorites refill to 80 %, and a full offload/reload triggers at 95 % (`RADIO_CONTACT_*_RATIO` in `radio_sync.py`).

## Sending

How a message leaves the program and how we know it arrived.

- Routers validate, then delegate to `services/message_send.py`. Radio access goes through `radio_operation()`.
- Channel slots: the count comes from firmware `max_channels` (fallback 40). Slots are reused through a session LRU cache, except on TCP (`connection_info` starts with `TCP:`) or with `app_settings.force_channel_slot_reconfigure`; then every send calls `set_channel(...)`.
- DM retries mirror `meshcore_py` `send_msg_with_retry`: stage the effective route with `add_contact`, send, and retry up to 2 more times only when `MSG_SENT` returned an expected ACK code. Timing follows the radio's `suggested_timeout`. The last retry is flood (`reset_path`). The first ACK is terminal: sibling ACK codes are cleared.
- ACKs are matched from the host `ACK` frame (`event_handlers.on_ack`) and from RF packets (PATH-embedded and standalone `ACK` payloads, in `packet_processor`). ACKs never update routes.
- Channel resend: byte-perfect within 30 s; `?new_timestamp=true` has no time limit and creates a new row. The sender prefix is stripped by exact match on the current radio name.
- Repeater/room login (`routers/server_control.py: prepare_authenticated_contact_connection`): one try on the effective route, then exactly one flood retry (`reset_path`), only on timeout and only when the route was not already flood. This is deliberate. The server relearns the return path on a flood login. Do not reduce it to single-shot.

## Read state

`GET /read-state/unreads` never windows the whole `messages` table. It enumerates conversations with an index skip-scan and reads through `idx_messages_pagination` / `idx_messages_unread_covering`. `tests/test_unreads_equivalence.py` keeps the old `ROW_NUMBER()` query as an oracle: both outputs must stay identical. `first_unread_ids` is the first unread row by `(received_at, id)`. Using `MIN(id)` would be wrong, because historical decryption inserts old messages with new ids.

## Region-scope stats (`GET /statistics` → `region_scope_24h`)

Two views with different denominators that are not meant to agree. Traffic (`path_utils.bucket_region_scope`) counts flood GroupText, including undecryptable packets. Senders (`StatisticsRepository._region_scope_senders_24h`, in `repository/settings.py`) counts distinct decrypted senders. `false_positive_floor` comes from undefined payload types (`0x0C`–`0x0E`) and measures corrupt captures that claim `TRANSPORT_FLOOD`. Show `scoped_messages` next to the floor, never the percentage alone, and do not remove the floor.

## WebSocket (server side)

- Events (`events.py: WsEventType`): `health`, `message`, `message_acked`, `message_deleted`, `contact`, `contact_resolved`, `contact_deleted`, `channel`, `channel_deleted`, `raw_packet`, `community_packet`, `community_live`, `error`, `success`.
- On connect the server sends `health` only. Contacts and channels load over REST. The client sends the text `ping`, and the server replies `{"type":"pong"}`.
- Each client has a bounded queue (`CLIENT_QUEUE_MAX` = 2048) drained by one writer task, so `broadcast_event()` never awaits socket I/O. `raw_packet` frames are dropped for a client whose backlog reaches 1024. A send timeout (5 s), a send error or an overflow evicts the client with close code 1013. Never call `websocket.send_text` on a managed socket: use `ws_manager.send_raw`.
- `broadcast_event()` also notifies the radio proxy and, when `realtime=True`, dispatches `message` → fanout + Web Push, `raw_packet` → fanout and `contact` → fanout. Historical decryption passes `realtime=False`.

## Community client

How Meshloom talks to the optional Meshloom Community service.

### HTTP (`services/meshloom_community.py`)

- Effective config = the DB (`community_enabled`, `community_iata`) plus the fixed addresses `DEFAULT_BROKER_HOST` / `DEFAULT_API_BASE`, read at call time by `get_community_effective()` (tests `monkeypatch.setattr` them; nothing imports them by value: the Stats publisher takes `state.broker_host`). No env var is read: a new DB starts off (opt-in in the UI). `services/legacy_env_settings.py` handles the retired `MESHLOOM_COMMUNITY*` variables: `import_legacy_community_iata()` (lifespan) copies a valid `MESHLOOM_COMMUNITY_IATA` into an existing DB once (marker `community_env_imported`, migration 091, which also empties the unused `community_broker_host` / `community_api_base` columns; a new DB ignores it), and `warn_about_retired_env()` warns at each start while any of them is set (they are in `RETIRED_ENV`). `GET /community` returns `enabled`, `iata`, `publisher_configured`, `publisher_connected` and `state` (`off`, `active`, `waiting_for_position`) only; `PATCH` accepts `enabled` and `iata`. `position_precision` values this version does not know (bind result, `/me/stats`) parse as `null`, so a successful bind never turns into a 500.
- Upstream mapping: transport error/timeout/5xx → **503**; 429 → 429; 400 → 400; 401 → 502 (with a clock hint when `classify_auth_rejection` reports `clock_skew`, drift > 60 s); other non-200 → 502 (`CommunityUpstreamError.upstream_status`); an unexpected body → 502.
- `CommunityBreaker`: 3 consecutive failures open it for 30 s (503 without network), then one trial call decides.
- Observer reach falls back to one GET per hash only when the batch route is missing upstream (404/405).
- The hashtag catalogue is global: `GET /community/hashtags` proxies `GET /v1/hashtags`. There is no per-IATA catalogue (`/community/iata/{code}/hashtags` was removed; Community answers 410 on its old `/v1/iata/{code}/hashtags`).
- Hashtag names go out (`PUT /v1/me/hashtags`) only with Community on and an IATA saved, and only for a `#` channel whose key is `SHA256(name)[:16]` (`is_public_hashtag_channel`); a `#` name on a channel with its own secret is private and never published. Resolve and sample uploads (`services/hashtag_catalogue.py`) also wait for the IATA.
- **Egress guard (two levels).** Opted out means no connection to the Community hosts or to the airport search (`api.fx-port.com`), with three exceptions: the leftover status clear below, the `PUT /v1/me/iata` of a join (`_bind_state`, see **Joining** below), the one request that leaves before the database says on, and the `POST /v1/me/opt-out` of an opt-out and of its manual retry (`_opt_out_state`, see **Opt-out call** below), which `stats_request` honours for that path only. Waiting for a position (on, but no publishable position) cuts the same connections, except the Stats MQTT publisher (status only, no packets) and the `PUT /v1/me/iata` binds: an IATA change and the automatic re-bind also pass then. `community_egress_state()` is the one check made by HTTP (`stats_request`), the Live socket (before every reconnect, and `subscribe`/`relancer`/`unsubscribe` through `community_active()`), the release mirror (`fetch_meshloom_latest`), `search_community_airports`, `active_iata_codes`, the hashtag name publish and resolve, and, through `community_active()`, `directory_is_available()` (so `directory_available` in the settings), the directory, observer reach and the update poll cadence. It answers None while off **and while waiting for a position** (below). The enrolled-level `community_enrolled_state()` (on, waiting or not) is used only by `FanoutManager.sync_system_modules()`, the Stats publisher (`MeshloomStatsPublisher._pre_connect`, before every reconnect, in case a stop abandoned its loop) and the `PUT /v1/me/iata` binds: an IATA change and the automatic position re-bind (`rebind_current_iata`, under `_update_lock`) set `_bind_state` around the `await bind()` only (`_with_bind_state`; never around the status retire or the publisher restore, whose spawned tasks would inherit it, and the spawned state transition clears it), which `stats_request` reads before the guard, so a chosen position can still be bound while waiting. `POST /me/iata/override` and every other `/v1/me/*` call stay cut while waiting.
- **Waiting for a position.** `community_state_of()` gives `waiting_for_position` when Community is on and `_position_missing` is set. `note_radio_position()` sets it as soon as an accepted identity (`ingest_allowed()`) reports a `self_info` with no publishable position (`publishable_position(self_info) is None`: none, `0, 0`, out of bounds). It runs right after the identity gate in `run_post_connect_setup` (the appstart `SELF_INFO` goes to the gate, not to the handlers), **before** `export_and_store_private_key`, so no packet and no authenticated call can leave first; then on every `SELF_INFO` and at the end of the setup, through `observer_position.note_radio_self_info()`. No radio, or an identity not accepted yet, keeps the last known state (owner decision Q2, no flicker). A position alone does not clear it: only a `PUT /v1/me/iata` that carried a position and succeeded does (`note_position_bound()`, from `put_iata_bind`), or a `self_info` whose position this process already bound (`position_already_bound`), so no packet leaves before Community has the position; a refused bind keeps waiting and the re-bind retries. The flag is persisted in `app_settings.community_waiting_for_position` (migration 092) and loaded by `load_position_state()` in the lifespan, before the update poll and the fanout start, so a radio known to be waiting makes no call at all after a restart (unauthenticated ones included: stats, hashtags, active IATA list, airport search, release mirror). A new database, or one migrated from 091, starts at 0 (not waiting) until the radio connects. Joining without a position is allowed and lands in this state (Q3). A change spawns `_apply_position_state()`: it saves the flag (also while off), then, under `_update_lock`, reads the state again; to waiting it bumps `_egress_generation`, cancels Community requests in flight and closes Live (`sync_community_live(False)`); back to active it reopens Live for its sessions and nudges the update poll; both ways the Stats publisher re-publishes its retained status at once (`FanoutManager.republish_system_status()`) and the `community_live` status broadcast makes every tab read `GET /community` again. Off, it only saves the flag. Covered by `TestWaitingForPosition` in `tests/test_community_off_no_egress.py`.
- **Opt-out call.** On an opt-out (`enabled` true to false, `PATCH /community` with an optional `opt_out_reason`: `privacy`, `not_useful`, `technical_issue`, `other`), `_update_community_locked()` first sets `_leaving` (`opt_out_in_progress()`): from then until the end of the teardown `community_enrolled_state()`, hence `community_egress_state()`, answers None, so the Stats publisher does not reconnect (`_pre_connect`) and shows no error toast (`_error_toast_allowed`, a `BaseMqttPublisher` hook) when Community kicks its session, and Live does not reopen. Then `_announce_opt_out()` saves the opt-out as pending (`app_settings.community_opt_out_pending`, JSON `{pubkey, reason, requested_at, iata}`, migration 093, write-ahead) and sends `POST /v1/me/opt-out` (`{"reason": ...}` or `{}`; JWT without the `iata` requirement, `_path_requires_iata`) through `_with_opt_out_state`, within `OPT_OUT_LAST_CALL_TIMEOUT_S` (5 s; its HTTP timeout, `OPT_OUT_LAST_CALL_HTTP_TIMEOUT`, is `httpx.Timeout(6, connect=2.5)`: a connection that never opens fails as a `ConnectTimeout` before the bound, a slow answer ends as a timeout). The result (`OptOutResult`) is `confirmed` for any 2xx (the body is not read), `maybe` for a timeout after the request left (Community may have recorded it; `_may_have_reached`), `failed` otherwise (refused, unreachable, connect timeout, no radio key). Confirmed empties the pending record. Community deletes the position, kicks the MQTT session, clears the retained status (at once, else by its own follow-up and reconciliation) and refuses the key (auth 10 to 15 s later, ingest, `403 opted_out` on the rest of `/v1/me/*` and Live) until a `PUT /v1/me/iata` re-join. The teardown gets the result (`community_teardown(before, opt_out=...)`): the publisher still clears the status in its own session at `stop()`, but the leftover status clear below is armed only for `failed`. `confirmed` also drops every clear still pending for that key and the recorded topic (`community_status_clear.drop_pubkey`), since the broker refuses them; `maybe` arms nothing and leaves the decision to the manual retry (idempotent upstream). The teardown also forgets the last bind (`observer_position.forget_last_bind()`), so a later `PATCH {enabled: true}` re-binds (`PUT /v1/me/iata`) even with an unchanged position, which is what lifts Community's refusal. A failure is logged and the local opt-out goes on (fail closed); the record stays and `GET /community` reports it as `opt_out_pending: {requested_at, reason}` while off. The record keeps the radio key; with the radio away it falls back to the key of the last published status topic (`last_published()`). Nothing retries on its own (owner decision Q7), not even after a restart: `POST /community/opt-out/retry` (`retry_opt_out()`, under `_update_lock`) is the only way, and the only Community request allowed by hand while off. It waits up to `OPT_OUT_RETRY_TIMEOUT_S` (20 s: the operator is waiting; connect 3 s, `OPT_OUT_RETRY_HTTP_TIMEOUT`). It answers 409 `no_pending_opt_out` when nothing is pending, 409 `opt_out_key_unknown` when the record has no key (never the radio connected now), 503 without a radio key, 409 `opt_out_other_radio` when the radio key is not the one that left, and the mapped Community error on failure (the record stays); on success it empties the record and drops the leftover clears for that key. A re-join (any off-to-on write) empties the record too. Covered by `TestOptOutCall` in `tests/test_community_off_no_egress.py`.
- **Opt-out teardown.** `update_community()` holds one lock (`_update_lock`), so an opt-in sent during the teardown waits for it instead of being undone by it; `sync_system_modules()` is serialised too, so two overlapping syncs never leave a second publisher running. It runs `community_teardown()` when `enabled` goes from true to false, in a `finally` block: a reset that raises after the write, or a cancelled caller (dropped request), still gets the whole teardown, and an opt-out tears down even when the write itself failed (fail closed). `_run_to_completion()` runs that work as a tracked task and holds the caller's cancellation until it is done; the move of the status topic on an IATA change is run the same way. Each step is bounded and runs even if the previous one failed: cancel Community requests in flight, close the Live relay (`close_stats()` bounds the close handshake and the reader, `CLOSE_TIMEOUT_S`), clear the retained MQTT status and stop the publisher, then reset the breaker, the sample quota and the Live queue. The status clear runs before the DISCONNECT through `BaseMqttPublisher._before_disconnect`: a retained `offline` first (QoS 1), then an empty retained payload (QoS 1), so a failed clear leaves `offline`, never `online`. Any other clean stop (reload, shutdown) publishes the retained `offline` only, as the Will would. If the broker is unreachable at that moment nothing is sent; the broker's own Will (`offline`, retained) covers a connection it saw drop, and that `offline` would stay. An IATA change clears the old status topic the same way (`FanoutManager.retire_system_status()`, which returns the module so the caller can read `retired_status_topic`), and an IATA change reopens the Live socket (the addresses are fixed, so only the IATA can move a topic or the Live target). `PUT /community/me/iata` (`bind_community_iata()`) follows the Community order for an IATA change, since `/authz` ties a status topic to the IATA of the MQTT session: under `_update_lock` it first clears the old retained status from the running session (still bound to the old IATA) and stops the publisher (`FanoutManager.stop_system_module()`), then calls `PUT /v1/me/iata`, then saves the IATA and starts the publisher with a JWT for the new one. A failed bind, or a caller cancelled at any point before the bind answers (the retire is inside the `try`), starts the publisher again on the old topic and leaves the stored IATA as it was. The UI changes the IATA with that call alone (no `PATCH /community` first). **Joining** is the same call with `enable: true` (`bind_community_iata(..., enable=True)`): while Community is off, the bind goes out first with a token carrying the requested IATA (the only request allowed while off besides the manual opt-out retry, through the `_bind_state` context variable read by `stats_request`), and only a successful bind writes `enabled` and the IATA and starts the publisher, so the first `online` never meets another bind (`iata_mismatch`). A refused bind (429 IATA change cap, 503 no radio key, ...) leaves Community off and the stored IATA unchanged. Without `enable`, the route still answers 403 while off. After a successful bind, the database write and the publisher and Live reload (`_update_community_locked`) run through `_run_to_completion()` too, so a caller cancelled in between never leaves Community on without its publisher. The very first bind of a pubkey is free (identity.md); `PATCH /community {enabled: true}` stays for API users (the settings no longer send it: they only leave through it): on an off-to-on change the route calls `note_radio_self_info(radio_self_info())`, so the automatic re-bind below refreshes the stored position (nothing is sent when the radio's `(public key, position)` is what the last bind sent). That PATCH does not bind first: the IATA already stored is bound by that re-bind, 5 s later, as a same-IATA bind. **The PATCH never changes the IATA**: an `iata` other than the stored one is refused with 409 `{"detail": {"code": "iata_requires_bind", "message": str}}` (`iata_through_bind`), whether Community is on or off and whether `enabled` is sent; the stored IATA itself is accepted (idempotent). Saved without a bind, it would reach the publisher (at once, or at the next opt-in) and the re-bind while Community still knows the old one, outside the retire → bind → reconnect order. An IATA change is `PUT /community/me/iata` (with `enable: true` to join); the frontend only PATCHes `{enabled: false}` (with an optional `opt_out_reason`).
- **Leftover status clear (the only connection after an opt-out).** `_retire_status_and_reload(before)` first saves the old topic (IATA, broker, audience, pubkey) in `app_settings.community_status_clear` (JSON list, migration 088), then retires and stops the publisher. If the publisher acknowledged the empty retained payload on that topic (`retired_status_topic`), the entry is removed; otherwise `services/community_status_clear.py` starts its worker. Each attempt holds `_update_lock`, saves the attempt count first, then opens one MQTT connection (no Will, JWT minted with that entry's `iata`, which the Community `/authz` requires to match the topic), publishes `b""` retained QoS 1 on the status topic, and disconnects, within `CLEAR_ATTEMPT_TIMEOUT_S` (15 s). At most `CLEAR_MAX_ATTEMPTS` (6) attempts, spaced by `CLEAR_RETRY_DELAYS_S` (1 min to 8 h), and none after `CLEAR_GIVE_UP_AFTER_S` (24 h from the opt-out): the entry is then dropped and the worker exits. It waits for this radio's key without spending attempts, and reads the key again under the lock. The lifespan resumes it at startup (`start_status_clear_worker`, before the fanout modules start) and stops it at shutdown.
- **Status topic left behind while stopped.** The Stats publisher records the last topic it made retained (`note_published`, `app_settings.community_status_last`, JSON object, migration 089; written only when it changes). At startup, before the fanout starts, `adopt_orphaned_status()` compares it with the effective state: Community off, or another IATA (database changed while the app was stopped) or another broker (a custom one retired by migration 091: `broker_host` stays in the recorded JSON on purpose, so that old broker gets one final clear), hands that topic to the same bounded clear (`mark_pending`, unless already pending) and forgets it. The public key is not compared (unknown before the radio connects). A retire (`_retire_status_and_reload`) forgets the topic once it is pending or cleared, and uses it in place of `target_for(before)` when the radio key is away. Covered by `TestOrphanedStatusAtStartup`. Being on again on the same topic drops the entry (`drop_current`), so a fresh `online` is never cleared. Community's ingest drops the empty payload as `invalid_json` before any bind or status write. Covered by `TestRetainedStatusClear` in `tests/test_community_off_no_egress.py`: one connection carrying only the clear, nothing after success, nothing after giving up (attempts or 24 h), survival across a restart, the old IATA's token. After an opt-out it is armed only when its `POST /v1/me/opt-out` surely did not reach Community (see **Opt-out call**).
- **Position in the bind** (`services/observer_position.py`). `PUT /v1/me/iata` is the only request that carries this radio's position, and `put_iata_bind()` is the only place that builds it: `publishable_position(self_info)` gives `lat`/`lon` to 6 decimals with `position_precision: "exact"` when the adverts carry the position (`advert_location_broadcast`: `adv_loc_policy` is an `int`, not a `bool`, other than 0), else rounded to 2 decimals (about 1 km) with `"rounded"`; nothing about a position when there is none (absent, not finite, out of bounds, (0, 0), or rounding onto (0, 0)). The browser cannot supply a position (`CommunityIataBindRequest` has no `lat`/`lon`; extra fields are ignored). `adv_loc_policy` missing or untrusted reads as off everywhere (`GET /radio/config` reports `"off"`).
- **Automatic re-bind.** A `SELF_INFO` subscription (`event_handlers.on_self_info`; every appstart: connect, `set_coords`, policy change), the end of the post-connect setup and `PATCH /community` turning Community on call `note_radio_self_info()`. When `(public key, publishable_position)` differs from what the last successful bind sent (kept in memory, so the first `self_info` after a start re-binds once), a worker waits 5 s (`REBIND_DEBOUNCE_S`), then sends the bind again with the stored IATA through `rebind_current_iata()`: under `_update_lock`, after `community_enrolled_state()` (so also while waiting for a position: this is how a chosen position reaches Community), with no status retire and no database write; Community does not count a same-IATA bind as an IATA change. Off or without an IATA it returns without any request, and so it does when, compared again under the lock (`still_needed`), a join or IATA change that held the lock already sent this position. Any exception (an `HTTPException`, or an unexpected body failing validation) is logged and counted as a failure, so the worker never dies. It waits for an accepted radio identity (`ingest_allowed()`), retries a failure after 60 s, 5 min and 30 min (a new radio change cuts the wait short), then, while Community still waits for a position (`waiting_for_position()`), every 30 min (`REBIND_WAITING_RETRY_S`) instead of giving up until the next radio change, and cannot loop (a bind does not change `self_info`). Covered by `tests/test_observer_position.py` and `TestPositionRebindOff`.
- **Ear position precision (`observer_reach.py`).** Community marks each ear position `position_precision: exact|rounded`. Only `exact` positions count in `max_distance_km` (and, in the browser, the mesh test distances, `meshTestObserverDistanceKm`); a `rounded` one still places the ear. A missing field reads `exact` on `/v1/directory/packets/*` (before the field existed these carried advert positions only, sealed copies included) and `rounded` on `/v1/directory/observers` and the `/reach` direct observers; `null` (a `/reach` coordinate completed by CoreScope, for instance) and an unknown value read `rounded`. `IataBindResult` and `MeStats` echo the stored bind's `position_precision` (`exact`, `rounded` or null). A later `exact` row for the same ear replaces a `rounded` one. Local advert fill (`_fill_local_contact_coordinates`, owner decision: by public key, never by name): an ear with no position or a `rounded` one takes the advert position of the contact with its full 64-hex public key (`get_by_key`, never a prefix) and becomes `exact`, so it counts in `max_distance_km`. An ear with no position and no such contact may be placed from the one contact with its name and a position, but marked `rounded` (map only, no distance or record, no key borrowed). An ear that has its own full key is never placed from a same-name contact with another key. So `position_precision: "rounded"` on an ear means "not usable for distances": a Community position rounded to about 1 km, or coordinates placed by name, which are not literally rounded. An `exact` ear keeps its own position. The browser does the same in the radio test: `placedObserverCoordinates` (`utils/meshTest.ts`) returns `byName: true` for a name-only placement (only for an ear without a full key), and `meshTestObserverDistanceKm` then gives no distance.
- Hashtag keys hash the exact name everywhere; the official-app normalisation is UI input only (see root `AGENTS.md`, "Hashtag rule").

### Live relay (`services/community_live.py`)

- One process-wide upstream socket to `/v1/live/packets`. The reader is claimed under the relay lock, so concurrent `subscribe()` calls cannot open two sockets. Sessions expire after 90 s without a heartbeat; the upstream closes 1.5 s after the last session leaves.
- Frames go out as `community_packet` through `ws_manager.broadcast`, i.e. to **every** connected WS client, not only to subscribed tabs.
- Reconnect backoff: 0.5 s doubling up to 30 s. It resets only after a socket stayed up ≥ 10 s (`JWT_EXPIRY_MIN_UPTIME_S`). The JWT is reminted locally on every attempt. A 4001 close on such a socket reconnects at once. Every backoff sleep (`_sleep_backoff`, 401 retries and pauses included) is spread by ±20 % (`BACKOFF_JITTER`, `jittered()`), so instances cut off at the same moment do not come back in step; a reconnect at once (0 s) stays at once.
- **Feed paused** (Community `KILL_LIVE_PUBLIC`): open sockets close with 1013 (`CLOSE_FEED_PAUSED`) and handshakes get 503 with body `code: live_disabled` (`is_feed_paused()`). The relay reports `state: paused` (no close code, no error) and retries after 30 s, then every 60 s (`PAUSED_RETRY_MIN_S`/`_MAX_S`, before jitter, so 24 to 72 s), whatever the socket's uptime. The first socket that opens clears the pause and resets both delays; any handshake answer that is not a pause (401, 409, 429, 502, `live_viewer_cap`, a 503 with an HTML body...), an opt-out and the end of the reader (`close_stats()`, no consumers left) clear it too, and each of them broadcasts the status (the 400 filter fallback and `close_stats()` included), so the browser's chip goes away. The egress guard still runs before every attempt. A 503 with another code (`live_viewer_cap`) or no body is not a pause: it stays a 4004 with the short backoff.
- A handshake 401 is not a 4001: retry at 2 s, doubling, and give up after 5 refusals (`AUTH_REJECT_MAX_ATTEMPTS`), or at once for `AUTH_FATAL_CODES`. The relay then reports `state: auth_rejected`, with `auth_error` = `clock_skew` or `token_rejected` (`auth_code` keeps the raw code). `POST /community/live/relancer` or `PATCH /community` clears it.
- Other handshake refusals: 409 maps to 4005, 429 and 503 (except `live_disabled`, above) to 4004; any other status, 403 included, has no close code. All of them reconnect with the normal backoff.
- 4002 is reserved and Community never sends it. If a 4002 close ever arrives, the reader stops that generation and waits for `POST /community/live/relancer`. 4003/4004/4005 are never shown to the user (`CommunityLiveStatus` hides them).
- `community_live.state` values: `connected`, `reconnecting`, `paused`, `opted_out`, `idle`, `auth_rejected`. `opted_out` also covers Community waiting for a position (the Live relay treats it as off).
- **Region filter.** `POST /community/live/subscribe` takes `iata` (list of codes, at most 64 (`LIVE_IATA_SELECTION_MAX`), the placeholders `XXX`, `LOC`, `AAA` (`LIVE_PLACEHOLDER_IATAS`, the set Community ingest uses) refused with 422; null or empty = every region), on the first call and on every heartbeat. Sessions are `{sid: (last_seen, regions)}`. The socket asks Community for `?iata=` = the union of the sessions' regions **plus the radio's IATA**, sorted; one session for every region, or more than 16 codes (`UPSTREAM_IATA_MAX`), means the global feed. When the union changes (subscribe, unsubscribe, a session expiring), a check runs after 2 s (`FILTER_DEBOUNCE_S`) and, if the open socket asked for something else, closes it and opens a new one with the same `X-Live-Instance`. That check goes through `community_egress_state()` before and after the close, so an opt-out in between never reopens anything. A handshake **400** on a filtered URL (`live_bad_filter`) switches to the global feed at once. For an hour (`FILTER_RETRY_S`) no union change or reconnect asks for a filter again; `relancer`/`PATCH /community` clear that hour at once. Past it nothing retries on its own: the global socket stays until the next union change or reconnect (JWT expiry, for instance). A Community that ignores the parameter just sends the global feed. Either way frames still go to every WS client, and the browser filters them again (frontend `AGENTS.md`, `#live`). `CommunityLiveStatus.upstream_iata` reports the filter of the open socket (null = global). A region change that lands while a handshake is in flight is checked again once that socket opens. The "heard by" counts in conversations are also bumped live by this feed (frontend `applyCommunityPacketObserverTick`, whatever regions the Live tab shows), then reconciled by REST. Because the radio's IATA is always in the upstream filter, packets heard in its region stay complete; accepted limit: a far observation of a packet never heard in the radio's region no longer bumps the count live, only on the next REST poll. `#test` only polls REST (`GET /directory/packets/{hash}/reach`), so the filter does not change it.
- `GET /community/iata/active` proxies Community `GET /v1/iata/active` (`[{code, unique_hashes_24h}]`, the placeholders `XXX`, `LOC`, `AAA` dropped), cached 60 s. Opted out or waiting for a position it answers `available: false` without any request; a Community without the route (404/405) gives `available: false` too (cached); other failures are raised as usual.

## Updates

How the program learns that a new version exists and, on some installs, installs it.

Security principle (root side never reads anything the app writes): see the root `AGENTS.md`.

- `services/install_kind.py`: `MESHLOOM_INSTALL_KIND` (`package|compose|addon|container|source`) wins. Otherwise detection order: package helper (`/usr/lib/meshloom/apply-update` or `meshloom-update.service`), compose helper (`MESHLOOM_UPDATE_HELPER=compose` or `/var/lib/meshloom/update-helper-compose`), container, source. Apply is supported only for package/compose with a helper present. `addon` is declared only, never inferred, and never applies. `MESHLOOM_UPDATE_HELPER=none` forces apply off.
- `services/oss_updates.py`: polls once at start, then every 300 s with Community on and every 6 h opted out or waiting for a position, or when the Community state cannot be read (`poll_interval_seconds`; turning Community on wakes the loop, `nudge_oss_update_poll`). It reads GitHub `releases/latest` (redirect, strict `X.Y.Z`) and, with Community on (not waiting) only, falls back to the Community mirror `GET /v1/meshloom/latest` (no JWT, skipped while the breaker is open). `source` in `GET /updates` says which one answered.
- `services/update_apply.py`: the app only writes the trigger `request-update` and its own `update-attempt.json`. The root helper publishes `status.json` (package: `/var/lib/meshloom-update/status.json`; compose: `MESHLOOM_UPDATE_STATUS_PATH`, a read-only mount). `read_job()` shows the attempt until the helper's `started_at` is at or after the request (±2 s), then the helper status. Helper `cooldown` shows as `failed`. The pre-4.18 `update-job.json` is read only as a fallback (`legacy_update_helper`). When the package `.path` unit is not active, the app falls back to `systemctl start --no-block meshloom-update.service` and checks that the unit really started.
- Routes: `GET /updates`, `POST /updates/refresh`, `POST /updates/apply` (202; 409 `apply_not_supported` / `update_not_available` / `apply_in_progress`), `PATCH /updates/settings` (`auto_update` and window; not through `PATCH /settings`). Auto-apply waits 6 h after a failed job.
- Tests: `tests/test_update_apply.py`, `tests/test_install_kind.py`, `tests/test_oss_updates.py`, `tests/test_update_helpers_exec.py` (runs the real helpers against hostile inputs).

## Telemetry polling and alerts

Repeaters and contacts that the user tracks are polled for telemetry (`radio_sync.py`), up to 8 tracked repeaters and 8 tracked contacts (`routers/settings.py`). The polling interval is one of 1, 2, 3, 4, 6, 8 (default), 12 or 24 hours. Repeaters and contacts each have their own ceiling of 24 checks per day, so the shortest allowed interval grows with the number of tracked nodes in that list (`telemetry_interval.py`); the stored choice is not changed, only clamped. With `telemetry_routed_hourly`, nodes reachable by a direct or routed path are also polled every hour. Each node keeps its samples for 30 days or 1000 samples, whichever comes first (`repository/repeater_telemetry.py`, `repository/contact_telemetry.py`).

After each poll, `telemetry_alerts.note_telemetry_poll()` evaluates the rules. Untracked nodes never alert, and a poll skipped because the radio was busy is not counted as a miss. Tracking a node writes a per-node override with `alerting: false` (`alerting_off_patch`), so its alerts stay off until the user turns them on. The rules are:

- gauges with a threshold and a re-arm margin (hysteresis, not a time window): `battery` (on by default, below 3.5 V), `noise` (on, above -90 dBm), `rssi`, `snr`, `tx_queue` (off by default), and scalar CayenneLPP readings such as `lpp:temperature` (off by default);
- `silence`: alert after N polls without a usable reply (default 2, between 1 and 4);
- `gps_lost`: a node that used to report a GPS fix stops reporting one.

Rules and per-node overrides live in `app_settings.telemetry_alert_rules`; the on/off state of each alert in `telemetry_alert_state`. Delivery goes through `notify.dispatch_system_event()` to any of three transports: Web Push (on by default), email (an Apprise `mailto` URL built on the fly from the SMTP settings, never stored as a URL; the HTML references the logo as `cid:meshloom-mark.png` and the PNG from `app/assets/` is attached with `inline=yes`, so the message is `multipart/related` and opening it fetches nothing: no remote image, no link) and a signed webhook (`X-Webhook-Event`, optional `X-Webhook-Signature: sha256=<HMAC of the body>`). Failures are only logged at debug level. SMTP password and webhook secret are stored in `app_settings.notification_destinations`; the API returns them as `********` and a PATCH that sends `********` back keeps the stored value. `POST /settings/notification-destinations/test` sends a fixed test alert on the email or the webhook channel (400 when it is not configured, 502 when the send fails). `GET /settings/telemetry-alert-catalog` lists the metrics a node can alert on.

## Web Push (`app/push/`)

Per-browser subscriptions in `push_subscriptions` (`UNIQUE(endpoint)`). VAPID keys are generated on first start and stored in `app_settings`. The subject is `app_settings.vapid_subject`, falling back to `DEFAULT_VAPID_SUBJECT` (`push/vapid.py`); Apple rejects `.local`. `MESHCORE_VAPID_SUBJECT` is no longer read (one-shot import, `services/legacy_env_settings.py`). Enablement: `policy.conversation_is_enabled` (overrides > `new_dm` for PRIV and rooms > public/hashtag ON > private-key channels OFF). Muted channels are a separate breaker. First-seen alerts (`dispatch_first_seen`) fire only on a new contact insert after setup. A push service answering 404/410 deletes the subscription. Requires HTTPS and outbound internet.

## Known non-issues

- `meshcore` 2.3.15 `confirm_factory_reset()` sends `0x33` without the `reset` suffix the firmware requires, so it does nothing; Meshloom sends the raw frame `b"\x33reset"` through `mc.commands.send()`.
- `sender_timestamp` is 4-byte Unix seconds on the wire. Dedup is per second, and switching to milliseconds would break echo dedup.
- Our own DM heard back over RF (`try_decrypt_dm` with `is_outbound`) attaches `packet_hash` to the plaintext row stored by the send endpoint. It does not create a second row.
- Contact lat/lon `0.0` is MeshCore's "no GPS" value and overwrites older coordinates on purpose.
- `meshcore_py` can raise `IndexError` on a truncated advert `LOG_DATA` frame. This is a one-off parser failure, not DB corruption.
