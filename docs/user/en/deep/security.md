Meshloom is designed for a network whose users you know. Several design choices only make sense under that assumption. These choices are deliberate, not oversights.

## What accounts protect, and what they do not

**Accounts are keys, not walls.** From 5.0 every page and every API route needs a signed-in account, and the server checks its role on each request ([Accounts and access](/en/docs/deep/access/)). That keeps strangers out; it does not limit what a person you let in can do. An administrator can read the whole history, send messages as your node, change the radio's settings and write extensions; a member can send as your node. Give accounts only to people you trust with the node.

**Other web pages are kept out.** The interface works from any device that opens Meshloom's own address. Another web site open in the same browser is a different *origin*: the server gives it no CORS access (same-origin only), so it cannot read the API's answers, and it refuses changes (`POST`, `PUT`, `PATCH`, `DELETE`) that a browser sends from another site, with or without a session. The session cookie is also `SameSite=Lax`. If you use a dashboard or a script served from another address, list that address in **Settings > Local Configuration > Allowed origins** (one `scheme://host[:port]` per line, empty by default, no `*`); each listed site can then do everything the signed-in user can, including the live connection below. Scripts and apps that send no `Origin` (curl, a phone app, a Home Assistant sensor) are not browsers: they sign in with a session or an [API token](/en/docs/deep/access/#api-and-device-tokens).

The live connection (`/api/ws`, the WebSocket) needs the same account and is refused when a browser opens it from a page of another site, so such a page cannot listen to your messages and packets as they arrive. Its `Origin` must match the address the browser asked for (`Host`, or `X-Forwarded-Host` behind a proxy that rewrites `Host`) or be one of the **Allowed origins**, compared the same way as for the API (case, default port and international domain names do not matter); clients that send no `Origin`, such as scripts, are accepted, but still need a token or a session. What a WebSocket receives follows the role: a `viewer`, a `kiosk` or a token without `read_private` never gets the text of a direct message. See [HTTPS](/en/docs/deep/https/#websocket).

**DNS rebinding.** Meshloom also looks at the name in the browser's address. In 5.0.0 an unknown name is only noted; from 5.1 it will be refused unless you declared it (see [Host names Meshloom answers to](/en/docs/deep/https/#host-names-meshloom-answers-to)). A trusted-network rule always checks it strictly.

**Extensions run Python.** An extension is a small Python program, bundled, installed or written by an administrator in the interface. It runs in a process of its own and can only ask Meshloom for what its accepted permissions allow; how strong the walls around it are depends on the installation ([Isolation](/en/docs/deep/plugins/#isolation)). Where there are none (isolation `none`), an administrator can still get code running on the host machine. This is intentional. The Python bots of 4.18 and earlier, which ran with no limit at all, became extensions in 5.0.0 ([Bots from 4.18](/en/docs/deep/plugins/#bots-from-418-and-earlier)).

**The radio proxy has no login.** See [Radio proxy](#radio-proxy) below.

None of this weakens MeshCore's own encryption over the air: direct messages and channel messages stay encrypted as usual. These points describe who can use the application, not what travels over the air. The node's private key is the exception on the server side: any administrator can read it (see [The node's private key](#the-nodes-private-key)).

## Signing in

Signing in is mandatory and uses accounts: a password of at least 12 characters, optionally a second factor (an authenticator app, recovery codes) and passkeys. Wrong passwords slow the next attempts down without ever locking an account, and sensitive actions are written to an audit log that administrators read. All of it is in [Accounts and access](/en/docs/deep/access/). Without HTTPS the password travels in clear text on every sign-in, so pair it with [HTTPS](/en/docs/deep/https/) beyond a network you trust.

Up to 4.18 the only lock was a shared HTTP Basic login (`MESHCORE_BASIC_AUTH_USERNAME` and `MESHCORE_BASIC_AUTH_PASSWORD`). On the first start of 5.0 it becomes the administrator account, then Meshloom stops reading the variables and warns while they are still set: remove them. Scripts that send it with `Authorization: Basic` keep working until 5.2 ([The 4.x Basic login](/en/docs/deep/access/#the-4x-basic-login)). On the Home Assistant add-on, Home Assistant signs you in through the sidebar; its port 8000 is not published by default, and where you publish it a Meshloom account is asked.

## Lock extensions

`MESHCORE_DISABLE_PLUGINS=true` locks the extension system at startup. No extension can be installed, changed or started, whatever the settings say; you can still view and delete them, and pause them all. Extensions restored from a backup come back turned off. The Linux package leaves it unset (commented out in `/etc/meshloom/meshloom.env`). See [Plugins](/en/docs/deep/plugins/) for the other ways to stop extensions.

## The node's private key

Meshloom reads the radio's private key each time it connects to the radio, if the radio's firmware allows it, and keeps it in the server's memory only. Meshloom never writes it to its database. If the firmware refuses, Meshloom works without it, but it can no longer decrypt direct messages on the server, and a backup then holds no identity. Encrypted photos in direct messages use it too: Meshloom derives from it, in memory, the secret shared with the contact (see [Encrypted files](/en/docs/deep/share/#encrypted-files)).

The key can always be read back by any administrator: `GET /api/radio/private-key` returns it as hexadecimal text, and both the configuration export in **Settings > Radio** and the full backup in **Settings > Database** contain it (see [Back up your radio](/en/docs/backup/)). There is no switch to turn this off. Another web site open in the same browser cannot read them (see [What accounts protect, and what they do not](#what-accounts-protect-and-what-they-do-not)), unless you listed it in **Allowed origins**. Keep Meshloom on a network you trust, and treat the backup file like the key itself: encrypt it with a passphrase when you keep it anywhere else than on that network.

Importing a key (**Set Private Key**, write-only) never shows the key. A key that does not match the radio the database is bound to is refused until you confirm the identity change (see [First launch](/en/docs/first-run/)).

On Linux, the server also marks itself as not dumpable at startup, so another program running as the same user cannot read its memory or its environment (where a 4.x Basic login set in the environment would live). The cost: the server writes no core dump, and debugging tools such as `py-spy` or `gdb` need `sudo` to attach to it. This protects against other non-root programs and does nothing against root; the default Docker image and the Home Assistant add-on run as root, so the protection mainly matters for the deb/rpm packages and installs that run as a dedicated user.

## The sharing key

Link and file sharing does not use the radio's key. Meshloom creates a separate key for it, at random, the first time sharing needs it, and keeps it in its database. To the sharing service this key is a pseudonym: it groups your uploads and your quotas, and it is not linked to your radio's public key in the Community directory, so what you share cannot be tied to your node, a ban there has no effect on Community, and a new radio keeps the same sharing identity. Only its public half leaves the server, in the short signed tokens sent to the sharing service: each one is valid for under two minutes, for one request only.

The key never appears in the settings API, the support snapshot, the logs or any backup: the full backup and the JSON backup refuse to include it, and the `meshcore.db` download has it cleared. After a restore, Meshloom gives the instance a new sharing key; what you shared before stays online until it expires, but is no longer listed as yours. Other features that need their own key (remote access) get a separate one, so the two cannot be linked to each other.

**Photos on disk and when they are read.** A photo you share is checked in the `share-tmp` folder, readable by Meshloom only, and deleted right after, whether the upload worked or not. The `share-cache` folder keeps the photos Meshloom has downloaded, 200 MiB at most and one hour each (see [Other install paths](/en/docs/deep/install-paths/#database-and-updates)): a public photo as the service holds it, an encrypted one only as sealed bytes, which Meshloom decrypts at each view and sends to the browser with an instruction not to cache it. Reading a photo needs the right to read the conversation it is in, and a photo in a direct message needs the right to read direct messages. Meshloom serves every photo as an image that a browser cannot run as a page (`nosniff`, no script allowed), after checking that its real type and dimensions are those of an image.

**Encrypted files.** An encrypted photo is sealed on the server with AES-256-GCM, under a key derived (HKDF-SHA256) from the secret of the conversation and from the file's identifier: the key of a private channel, or the secret shared between your radio's key and your contact's. That secret never reaches the browser (which names a channel by an opaque identifier) nor the service. The server refuses encrypted files on the Public channel, in hashtag channels and on room servers, because there the key is known to everyone or can be computed from the name. The sealing has no forward secrecy: anyone who holds the key of the conversation, now or later, can read every sealed file they saved or that is still online. See [Short links and photos](/en/docs/deep/share/#encrypted-files).

## Radio proxy

**Settings > Proxy** can make Meshloom behave like a radio on the network, so a phone app or a second Meshloom can use your radio through it. It is off by default. The protocol it speaks has no authentication, and accounts do not cover it: it listens on every interface (port 5051 by default), and anyone who can reach that port can use your radio, send as your node included. This is a decision, not an oversight: the apps that speak the protocol cannot sign in. Enable it only on a network you trust and never forward the port to the Internet.

## Wi-Fi password

Meshloom never stores the radio's Wi-Fi password, in its database or in its logs, at any log level. To know whether credentials are stored, it reads the password back from the radio over the companion link, then forgets it: after each connection, at each retry of that check, and on a manual **Retry** while no check has completed. Storing credentials sends the password to the radio and reads it back twice (once before, once to verify). Over a TCP transport the companion link is not encrypted: the password crosses your local network in clear each time Meshloom reads it back or stores it, and anyone who can watch that network can read it. Over USB or Bluetooth it does not cross your network. See [Radio, contacts, and channels](/en/docs/deep/radio/#wi-fi).

## Integration and notification secrets

Once saved, the secrets of your integrations and notification destinations are never shown again: the Apprise addresses, the webhook URLs, header values and HMAC secrets, the MQTT passwords, the Amazon SQS access key ID, secret key and session token, and the SMTP password. The API, the support snapshot and the integration statuses show `********` instead; the Apprise list shows only each service and host, a webhook URL only its scheme and host, and a header only its name. An integration's error never quotes the password or the tokens of its Apprise address or webhook URL, nor a header value, only the service and host. Changing where a secret goes (a webhook or notification URL, an MQTT broker, its port or TLS, an SQS endpoint, the SMTP server, its port or security) requires typing the secret again (for a webhook: its header values and HMAC secret), and a restore that points a secret somewhere else drops it with a warning. The JSON backup download (`GET /api/settings/backup/json`) leaves out the SMTP password, the notification webhook URL and secret and the Apprise notification URLs; restoring it keeps the ones already stored. The full backup in **Settings > Database** still holds the secrets of the integrations (MQTT, fanout webhooks, Apprise outputs, SQS): encrypt it with a passphrase. The notification **channels** and **destinations** (e-mail, webhook, Apprise) are the exception: their secrets (passwords, tokens, addresses that carry a token) are never written to any JSON backup, full or not. A restore recreates those channels switched off, marked *Secret missing after a restore*, until you type the secret again; the support snapshot lists each channel with the names of its secrets that are set, never their values. Which fields are secrets depends on the type: the SMTP password, a webhook URL and its HMAC secret, the ntfy topic, token and password, the Discord webhook URL, the Telegram bot token, the Gotify token, the Home Assistant token and the Apprise URLs. Anyone who can create or edit a channel can send your notifications elsewhere, so channels are administrator-only; see [Configure channels from a trusted network](/en/docs/deep/notifications/#configure-channels-from-a-trusted-network).

## Support snapshot

**Settings > About > Open debug support snapshot** (`/api/debug`) is meant to be pasted into a bug report. Outside the logs it holds versions, settings and counters, never the private key; the keys of contacts and channels appear only as one-way fingerprints. The logs never contain the private key or a Wi-Fi password, at any log level, `DEBUG` included. The logs can contain channel names and channel keys at any level; at `DEBUG` they can also contain repeater and room login passwords and the Bluetooth PIN. Stop copying at the line `STOP COPYING HERE` to leave the logs out.

## What leaves your machine

What each output sends depends on the scope you give it in **Settings > MQTT & Automation**.

- **Community Sharing** only ever carries raw radio packets to a community MQTT server, never readable conversation text.
- **Private MQTT**, **Webhook**, **Apprise** and **Amazon SQS** can carry the full text of messages, according to the channels and contacts you select.
- **Notification channels** (Settings > Notifications) send the events you tick to the service behind each channel: the push services of the browser makers, your mail server, a webhook, ntfy, Discord, Telegram, Gotify, Home Assistant or any Apprise service. For a third-party service (Discord, Telegram, ntfy.sh, an e-mail relay outside your network), the text of direct messages and private channels stays home by default (title only, "Message from Léa"); with *Always*, it leaves too. When you forward other people's messages to such a service, **you**, the operator, are the one responsible for that data (in the EU, the data controller). Public services such as ntfy.sh keep messages for a while (12 hours by default on ntfy.sh) and anyone who knows the topic can read it: choose a long, random topic, or your own server. Nothing goes through TwinRocket. All of it is explained in [Notifications](/en/docs/deep/notifications/#privacy-and-what-leaves-your-machine).
- **Link and file sharing** (off until an administrator accepts its terms) sends the address you shorten or the photo you share to `meshl.ink`, run by the project, with this Meshloom's IP address and its pseudonymous sharing key; reading a shared photo asks the service for it by identifier, and shortened links shown with a hint are looked up the same way. Nothing is sent from your browser, and nothing is requested for a photo before you tap it or the preview setting lets it load. See [Short links and photos](/en/docs/deep/share/#what-leaves-your-machine).
- **Map Upload** sends the adverts of repeaters and room servers, with their position, to a map service (map.meshcore.io or one you choose).
- **Home Assistant** publishes your devices to the MQTT server (broker) you configure.

The notification channels (webhook, Apprise and the other types), Web Push and the fanout Webhook, Apprise, Amazon SQS and Map Upload outputs only reach destinations on the Internet unless you allow a private network for them (see [Notifications](/en/docs/deep/notifications/#destinations-on-your-network) and [Fanout](/en/docs/deep/fanout/#destinations-on-your-network)): a page that changes these settings cannot make the server probe your network. Meshloom never follows a redirect for them and always refuses cloud metadata addresses. The webhooks, Web Push and Map Upload connect only to the address that was checked. Apprise and Amazon SQS connect on their own after the check, so someone who controls the DNS of a host name you typed could still point it elsewhere; Apprise accepts only the services listed in [Fanout](/en/docs/deep/fanout/#apprise).

Some features need Internet access: [notifications](/en/docs/deep/notifications/) (and [push](/en/docs/deep/push/) for browsers), and [Meshloom Community](/en/docs/deep/community/) when joined (raw-packet publishing, directory, sharing of hashtag channel names). Even with both off, Meshloom checks GitHub for new releases once every 6 hours (with Community on: every five minutes, with the Community mirror as a fallback). It keeps working if that check fails. When you leave Community, Meshloom sends it one last request to record the opt-out and delete your radio's position. After that, it is reached again only if Community surely did not receive that request and the status of your node could not be deleted from the broker at that moment (a single reconnect deletes it, a few tries at most within 24 hours, then nothing), or when you press **Retry** because Community did not confirm the opt-out (see [Meshloom Community](/en/docs/deep/community/#leaving)). Alert e-mails carry the Meshloom logo inside them, so opening one loads nothing from the Internet.

## Trusted networks

A trusted network rule signs a device in without a password (see [Accounts and access](/en/docs/deep/access/#trusted-networks)). It never applies through a reverse proxy, a tunnel, Meshloom Remote or Home Assistant ingress, nor from this machine's loopback outside the add-on, and only when the browser uses an IP address or a local name. Keep the list empty unless you need it, and never map a network to an administrator you would not hand the machine to.

## A reasonable posture

- Give accounts only to people you trust, each the weakest role that does the job; turn on two-factor authentication for administrators, and **Require two-factor authentication for administrators** when Meshloom can be reached from the Internet.
- Never expose port 8000 or the radio proxy port directly to the Internet. For remote access, use a VPN, or a reverse proxy with HTTPS that you list in **Trusted proxies**.
- Set `MESHCORE_DISABLE_PLUGINS=true` if you do not need extensions.
- Encrypt a full backup with a passphrase when you store it away from that network.
- Always serve Meshloom over HTTPS beyond a network you trust: the session cookie and the password travel in clear over plain HTTP.

The short version is in [A trusted network](/en/docs/trust/).
